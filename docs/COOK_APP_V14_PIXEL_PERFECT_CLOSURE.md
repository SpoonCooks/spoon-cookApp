## 7. The five-minute extension rule

> The extension element remains for five minutes only, then the UI returns to the normal Active Job
> screen.

Implemented as a transient projection in `@core/domain/serviceState`, covered by 15 tests in
`src/__tests__/extensionWindow.test.ts` at the exact boundaries the brief asks for (confirmation,
4:59, 5:00, past 5:00, repeated polls, restart, interruption, End-OTP).

`extensionBannerRemainingMs` is the difference between **two server instants** —
`extension.confirmedAt` and the snapshot's `clock.serverNowIso`. Consequences, each asserted:

- A device clock change cannot lengthen or shorten the window.
- Repeated polls can only decrease it; it never reopens.
- A restart reconstructs the same answer, because nothing is carried across the restart.
- The extension itself survives the banner: after the window closes, `expectedEndIso` is still the
  extended end and `isExtended` is still true. Losing the banner is not losing the extension.

### The missing backend contract (precise)

`GET /v1/cook/jobs/:id` **does not send a confirmation timestamp.** The value exists in the
database — `booking_extensions.settled_at` (migration
`1754313000000_phase8_cancellation-refunds-extensions.sql`, line 276) — but the cook read model
`src/cooks/projections.ts` (lines 209-210) selects only `state`, `minutes` and `new_expected_end`.

Required change, backend side: add `settled_at` to the cook extension projection as
`extension.confirmedAt` (ISO-8601).

Client side this is already handled: `schemas.ts` parses `confirmedAt` as
`isoString.nullable().optional()`, so the field is honoured the moment it appears with **no client
release**. Until then it parses to `null`, the window computes `0`, and the `622:1163` banner never
draws against production data while the extended timer still runs. That is the safe failure, and it
is asserted by `never shows the banner against today's production payload`. No confirmation instant
is invented — not from "first time the app saw the extension", not from the device clock.

The backend was **not modified**. `D:\spoon-backend` was read only.

## 8. A design contradiction that must be resolved

The lead job card escalates through three colourways. The frame names give thresholds that the
frames' own content contradicts:

| Frame     | Name               | Countdown it draws | Border / disc / chip / CTA                                     |
| --------- | ------------------ | ------------------ | -------------------------------------------------------------- |
| `583:427` | `next in <45 mins` | `25 mins`          | `#ffd600` / `#ffe666` / `#ffef99` / `#ffd600`, label `Chalo`   |
| `583:453` | `next <10 mins`    | `20 mins`          | `#cfff04` / `#ecff9b` / `#ecff9b` / `#cfff04`, label `chalo!!` |
| `583:479` | `next <5 mins`     | `15 mins`          | `red` / `#fdd2d2` / `#fdd2d2` / `red`, label `CHALO!!` (white) |

`20` is not under ten and `15` is not under five. Either the names or the mock values are stale and
the file gives no way to tell which.

Rather than invent a threshold and paint a card red on the strength of it, the tier is an **explicit
input**: fixtures set it per frame so each gallery state reproduces its frame exactly, and
production passes `defaultJobUrgency` (`soon`, the calmest). Eligibility is untouched — whether the
cook may leave stays `isActionable`, a server ruling — so the open question costs a colour, never a
command. **Needs a designer or backend ruling.**
